## 2. Findings by severity

### BLOCKER — none.

### MAJOR

**MAJ-1. Re-entrant `trackIntent` inside an outcome callback makes the outer check apply an already-retired id twice (duplicate `dropped`/`errored` signal; stale memo). Regression vs the old live-set guard; the self-review's "re-entrancy is safe — `pending` is a copy" is wrong precisely because it is a copy.**
`packages/runner/src/speculation/overlay-destination.ts:976–1000` — `#checkIntents` snapshots `const pending = new Set(ids)` (:976) and `consider` (:978–987) gates on `pending.has(entry.eventId)` only. `#applyIntentEntry` (:1119) → `#notifyIntentOutcome` calls arbitrary subscribers synchronously. A subscriber that re-fires on the same sidecar (a retry-on-drop UI — exactly the hook events.md §5 mandates) calls `trackIntent` → an INNER `#checkIntents` on the same `ids` which retires X; control returns to the outer loop whose `pending` still holds X → the outer `consider` finds X's entry and runs `#applyIntentEntry(X)` AGAIN: `#untrackIntent` is a no-op, `retireIntent` a no-op, but `#settleIntentConsequence` re-memoizes a terminal outcome for X (the memo is "bounded by in-flight fires" — this entry is orphaned) and `#notifyIntentOutcome` delivers `dropped:X` / `errored:X` a SECOND time. With a retry-on-drop subscriber that is a DOUBLE re-fire of X (two fresh appends for one user action).
Reproduced with a scratch scripted test (seed entries [X, Z]; track both; subscriber re-fires once on the first outcome; one notification marks both dropped, hints Z then X): outcomes = `["dropped:Z","dropped:X","dropped:X"]`, `pendingIntentCount` 1 (the retry). The OLD `#scanIntentNotices` checked the LIVE `ids.has(...)` per entry and could not double-apply (and its `trackIntent` returned early when a sink existed, so no nested scan at all).
Latent today: no production `subscribeIntentOutcomes` caller exists (grep: only tests + the definition), so the user-visible impact is nil until a UI subscribes — but the hook is the ruled UI hook, so this should land fixed.
Fix shape (one line): in `consider`, gate on the LIVE set re-fetched from the map (the `ids` Set object can be deleted and recreated by the inner check): `const live = this.#trackedIntents.get(space)?.get(sidecarId); if (live === undefined || !live.has(entry.eventId)) { pending.delete(entry.eventId); return; }` before applying. Pin: the scratch scenario above (two marks in one check + a subscriber that re-fires) expecting exactly one outcome per id.

### MINOR

**MIN-1. Pin vacuity gap: a notification whose merged changes span TWO tracked sidecars is not covered — the mutation "record only the first wanted change per notification" (`doc-notification-listener.ts:136–143`, `break` after the first `#record`) survives every shipped pin.** Ran it: `speculation-intent-listener` 2/9, `event-append-client` 4/15, `speculation-arrival-gate` 1/6, `executor-effect-channel` 1/15 all GREEN under the mutation (8 passed / 45 steps). The TIP handles it correctly (verified with a scratch probe dispatching one notification with changes on two sidecars: both retired, 4 checks), so this is coverage, not behavior. Fix: a scripted pin that dispatches ONE notification with changes on two tracked sidecars (the harness's `deliver` takes one doc; extend it or dispatch to `scripted.subscribers` directly) asserting both retire. **MIN-2. Spec sentence says more than the code does.** `docs/specs/server-side-execution/speculation.md:123–125`: "the check runs in a microtask and is O(outstanding), never O(history)". In the code (a) the IMMEDIATE check at `trackIntent` (:832) is not in a microtask and walks the whole array for a fresh id (pin 5 itself asserts `visitsAfterTrack === 1000`; the build report §3 and the register's "Not rows" bullet :3998 admit it); (b) a notified check with no usable hint walks from the tail to the tracked entry — O(entries appended after mine), which on a busy shared stream with a stuck event is O(k) per notification, O(k²) cumulative (a plain JS walk, microseconds at k≈100, but not "O(outstanding)"). The design's own §3.3 wording ("O(outstanding + hints), degrading to a raw O(E) array walk only when a hint misses") and the ruling (item 4 says nothing about cost) are both weaker than the landed sentence. Fix: either soften the spec clause to the design's wording ("no transaction, no dependency; per notified check O(outstanding + hinted indices), a missed hint degrades to a raw tail scan") — or make the code meet it: memoize each located index into `state.hints` after the first location so later checks for the same id are O(1) (the hint machinery already exists; `#checkIntents` :988–1000), which also removes the O(k²) on busy streams. The register block is honest about this; only the spec sentence overclaims.

**MIN-3. The "tracked-set drain" gap deserves a NUMBERED row now, not "recorded, not a row" (`verification-coverage.md:3988–3997`).** The consequence is not only `waitForIntentConsequence` hanging: `cell.ts:1655–1680` (the `waitForIntentConsequence` await at :1670) routes the caller's durable-ack `onCommit` through `overlay.waitForIntentConsequence`, so a never-draining intent hangs the CLI verb dispatch / webhook-forwarder ack forever.
