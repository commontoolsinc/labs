# Unit test coding style

How a unit test file in this repository is shaped: where it lives, what it is
called, how its blocks nest, and which assertions to reach for.

Running the suites is covered in [`TESTING.md`](TESTING.md). Integration and
browser tests answer to different conventions —
[`UI_TESTING.md`](UI_TESTING.md) for reaching into shadow DOM, and
[`waiting-in-tests.md`](waiting-in-tests.md) for the rule against polling,
which applies to unit tests too.

Not every test file in the tree follows this guide, so a neighboring file is
not evidence of what to write. A new file follows this guide closely. An edit
to an existing file conforms the area around the edit; converting a whole file
is its own change, made deliberately rather than as a side effect.

## Where a test file lives, and what it is called

Unit tests go in a `test` directory directly under the package they test, not
beside the source file. Where the source tree has subdirectories, the `test`
tree mirrors them: a test for `src/codec-json/encode.ts` lives at
`test/codec-json/encode.test.ts`. That keeps a test findable from its source,
and its source findable from the test, as a package grows.

Name the file `<topic>.test.ts`, where `<topic>` is one of:

- The base name of the source file under test — `value-hash.test.ts` for
  `value-hash.ts`. This is the default.
- The name of a single class, function, or other export, when the file tests
  only that one thing — `SchemaAndHash.test.ts`. Prefer this when it applies.
- A `lower-kebab-case` phrase describing the subject, when the tests span
  several source files — `donut-cross-check.test.ts`.

A test file most typically concerns one main source file, but that is a default
rather than a requirement. Splitting one source file's tests across several
files is fine, especially when one of them goes deep on a single function.
Covering several source files from one test file is fine when that makes the
tests clearer or less repetitive. Being sensible beats holding the line.

## Structure

Use the BDD functions from `@std/testing/bdd` — `describe()`, `it()`,
`beforeEach()`, `afterEach()` — and `@std/expect` for assertions.

### One top-level `describe()`

Every test file has a single top-level `describe()` call containing everything
else. Its title is the name of the file under test without the source suffix:
`describe("donut-weight", ...)` for `donut-weight.ts`. As a special case, when
the source file exists only to export one class, the title names that class:
`describe("DonutWeight", ...)`.

There is one carve-out. When a file parameterizes the same test body across a
fixed set of implementations — typically one `describe()` per implementation,
generated by a loop — those generated calls may each be top-level. The expected
shape is one top-level `describe()` for the shared API surface, plus one per
implementation.

Group related tests with nested `describe()` blocks rather than comment
banners. A `describe()` title appears in the test run transcript, where it
tells a reader which group failed; a comment does not.

### Describing a class

Under the `describe()` naming a class, use literally
`describe("constructor()", ...)`, `describe("instance members", ...)`, and
`describe("static members", ...)` to hold the tests for its members. A test
that fits none of them — one cross-checking a static member against an instance
member, say — can sit directly under the class's block.

The `constructor()` block usually holds a plain sequence of `it()`s. Each
`... members` block usually holds one `describe()` per member, each of which in
turn holds `it()`s. Either may grow another layer of `describe()` when a group
of related cases earns one.

```ts
import { describe, it } from "@std/testing/bdd";
import { expect } from "@std/expect";

class DonutWeight {
  static readonly zero = new DonutWeight(0);

  constructor(readonly grams: number) {
    if (grams < 0) throw new Error("Weight cannot be negative.");
  }

  plus(other: DonutWeight): DonutWeight {
    return new DonutWeight(this.grams + other.grams);
  }
}

describe("DonutWeight", () => {
  describe("constructor()", () => {
    it("throws given a negative weight", () => {
      expect(() => new DonutWeight(-1)).toThrow();
    });
  });

  describe("instance members", () => {
    describe("plus()", () => {
      it("returns the sum of the two weights", () => {
        expect(new DonutWeight(3).plus(new DonutWeight(4)).grams).toBe(7);
      });
    });
  });

  describe("static members", () => {
    describe("zero", () => {
      it("is a weight of zero grams", () => {
        expect(DonutWeight.zero.grams).toBe(0);
      });
    });
  });
});
```

### Describing a function

A top-level function gets a `describe()` of its own, holding a sequence of
`it()`s, in the same shape as a method's block above.

### Writing the description strings

An `it()` description reads as a third-person singular verb phrase completing
the word "it": "returns `undefined` for an empty list", not "should return
`undefined`" and not "empty list".

Prefer describing the **observable output** over ascribing an intent. "returns
`false` for a bare function" beats "rejects a bare function": both are verb
phrases, but the first states a checkable fact about what the code does, and
the second describes a motive that no assertion can confirm.

Where the fact is a return value, the verb is **"returns"**. Specifically not
"answers": that casts the call as a question put to the code, which is a
metaphor standing in for a word that is already exact and already shorter. It
also splits the vocabulary of the suite, so that two files pinning the same
kind of fact no longer read as though they do.

Mark up descriptions in Markdown, the same as a comment — backticks around code
and code-like things. The one exception is a `describe()` whose title would
otherwise be entirely one backticked string: write `describe("eatDonut()")`,
not ``describe("`eatDonut()`")``.

Description strings may run past the 80-column line width the rest of the
repository holds to. A description that reads well is worth more than a
description that wraps well.

## Assertions

Default to `expect()`-style assertions — `expect(...).toBe(...)`,
`.toEqual(...)`, `.toStrictEqual(...)`, `.toThrow(...)` — over the `assert*()`
family. An `expect()` failure prints actual against expected, and structurally
diffs objects and arrays; a bare `assertEquals(a, b)` failure leaves the reader
to work out what differed. That difference is load-bearing exactly where tests
are hardest to debug.

- **Equality on structured values**: always `expect(actual).toEqual(expected)`
  or `.toStrictEqual(expected)`. Never `assertEquals` or `assertStrictEquals`
  on an object, array, or other composite — the failure output is strictly
  worse.
- **Strict equality on primitives**: `expect(thing).toBe(value)`.
- **Throwing**: `expect(() => fn()).toThrow(...)`.
- **Truthiness**: plain `assert(thing)` or `assert(!thing)` is the right tool
  when "is this truthy" _is_ the whole assertion, with no further structure to
  report. Never write `assertEquals(thing, true)`, which has the weaknesses of
  both forms; `expect(thing).toBe(true)` is also fine when the test reads more
  naturally as a strict-value check.

The boundary is semantic fit rather than taste. Reaching for `assert*()` is a
prompt to ask whether `expect()` would say the same thing with better failure
detail. When the `assert*()` form genuinely captures something cleaner, keep it
and say why in a comment.

## Which comparison decides the outcome?

Before writing a test whose whole point is a fine-grained distinction, ask
which comparison actually determines whether it passes: the matcher's, or the
code under test's. If it is the matcher's, the test is measuring the test
framework, and it will stay green no matter what the code does. A vacuous green
test is worse than no test at all, because it looks like coverage and so stops
anyone from writing the real one.

The check is mechanical: confirm the test **fails** against a deliberately
wrong expectation before finalizing it. A test that cannot fail is not
evidence.

The traps below all have the same shape — an operator that is correct for some
comparison, just not the one that was meant.

### Hazards of the JavaScript matchers

**`toEqual` cannot see negative zero.** `expect(-0).toEqual(0)` passes, and so
do the array and `Set` forms. Only `toBe()`, which uses `Object.is`,
discriminates `-0` from `+0`. Any `-0` assertion written with `toEqual` is
therefore vacuous. Assert the sign of zero with `toBe`, and where the value is
nested, reach in and assert the scalar rather than comparing the container.

**`toBe` answers the `NaN` question for you.** Both matchers treat `NaN` as
equal to itself, so `NaN` escapes the collapse above — but it has the opposite
problem. `expect(NaN).toBe(NaN)` passes because `Object.is` says so, whatever
the code under test decided. A test meaning to pin "this implementation treats
all `NaN`s as equal" has to route through the implementation's comparison and
assert on _that_ result:

```ts
import { expect } from "@std/expect";
import { valueEqual } from "@commonfabric/data-model/fabric-value";

// Vacuous: asserts `Object.is(NaN, NaN)`, which holds regardless of
// what `valueEqual()` does.
expect(NaN).toBe(NaN);

// Real: asserts what `valueEqual()` actually decided.
expect(valueEqual(NaN, NaN)).toBe(true);
```

Neither matcher is globally safe: `toEqual` is too coarse to see `-0`, and
`toBe` is precise enough to answer the `NaN` question in the code's place.

### Hazards specific to this repository

**`hashOf()` returns a boxed value.** Its result is a `FabricHash` object, not
a string, so `===` — and `toBe`, which is `Object.is` — compares identity
rather than hash value. Two structurally identical hashes of equal values
compare unequal. Compare through an accessor instead:

```ts
import { expect } from "@std/expect";
import { hashOf, hashStringOf } from "@commonfabric/data-model/value-hash";

const a = { donut: "cruller" };
const b = { donut: "cruller" };

// Wrong: compares object identity, and always fails.
expect(hashOf(a)).toBe(hashOf(b));

// Right: compares hash value.
expect(hashOf(a).bytes).toEqual(hashOf(b).bytes);
expect(hashOf(a).hashString).toBe(hashOf(b).hashString);

// Also right: `hashStringOf()` returns a plain string, which `toBe` compares
// by value. Reach for it when the hash is only ever wanted as a string.
expect(hashStringOf(a)).toBe(hashStringOf(b));
```

The same caution applies to any other boxed primitive that wears the costume of
a scalar. When a comparison between two values that ought to be equal comes
back false, **print the operands before believing it**. A `FabricHash` renders
as `FabricHash {}` rather than as a hash string, which is the tell. A
confidently reported defect that turns out not to exist costs more than a
missed gap: it consumes the reporter, the reviewer, and everyone downstream of
both.
